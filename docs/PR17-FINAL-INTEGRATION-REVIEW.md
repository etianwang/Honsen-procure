## P1: Newly granted scope misses history and can block Pull

`apps/server/src/sync/postgres-store.ts:1960` filters the change log by current scope after `sequence > cursor`; `:2033` advances to the last visible row. `apps/desktop/src-tauri/src/lib.rs:6559` replaces authorization snapshots without reestablishing history, and `:6377` refreshes them before reading the existing account cursor.

Example: supplier A and its price are logged before an unrelated visible material change. A B-only purchaser pulls and advances past the latter while A is filtered. Later an administrator grants A to this same account. Pull still starts after the old cursor, so the unchanged A supplier, quote, orders and references remain absent. If a later A price arrives for the missing supplier, the actual desktop projector inserts it into `local_material_prices` (`lib.rs:8286`), whose supplier foreign key is enforced (`migrations/0004_local_catalog.sql:43`, `lib.rs:1528`). The category quarantine checks material, not supplier, and the page transaction rolls back before cursor commit. Each retry fetches the same failing page; unrelated later changes cannot advance. Revocation followed by regrant has the same risk if cursor advances during the gap.

Minimum repair: provide authorization-aware historical catch-up on scope expansion/regrant, with an atomic, replay-safe account boundary and consistent ordering of referenced supplier/material data; retain pending outbox and conflict protections. Ensure missing supplier dependencies cannot permanently poison a page. Prove B-only Pull, grant A, historical A supplier/price/order recovery, a later quote, restart/retry, revocation/regrant, and no leakage or overwrite with actual PostgreSQL and SQLite projectors.

## P1: Invalid supplier/quote Push is accepted and poisons Pull

The shared event schema accepts arbitrary payload records (`packages/shared/src/sync.ts:43`); `SyncService.canWrite` admits a purchaser at `apps/server/src/sync/service.ts:240`. The new store check at `postgres-store.ts:250` verifies supplier country and quote relations but never validates the required supplier/price fields or payload ID before inserting and acknowledging them at `:1042` onwards. An authorized purchaser can submit a new supplier with only a valid `countryId`; it is accepted and published, yet the desktop `SupplierInput` deserializer/validator rejects it (`lib.rs:8219`), rolling back the Pull page and cursor. A quote with just existing `supplierId` and `materialId` similarly lacks currency and amount and can be accepted. A later good update cannot rescue clients stuck on the earlier bad event because the change log retains that event.

This trust-boundary gap also existed on the target baseline, but directly violates this PR's stated illegal supplier/quote Push and safe integration acceptance. The final-head PostgreSQL test `apps/server/src/sync/formal-issue-hardening.test.ts:310` itself asserts that incomplete supplier and price payloads are accepted; both final-head CI runs passed that test. The test calls the store directly; the purchaser service path was checked statically, not exercised over HTTPS in this review.

Minimum repair: validate complete canonical upsert payloads and match payload ID to entity ID at the server boundary before accepted persistence, retaining authorized tombstone compatibility. Change fixtures to valid payloads and add real service/PostgreSQL malformed supplier and quote rejection plus Pull-progress tests. Establish a safe audited recovery for already published malformed history without silently dropping it.
